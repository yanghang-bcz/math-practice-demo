### 安全域名白名单的判定手法（可复用）

新域名最容易漏的一环：云开发的 **WEB 安全域名**如果没加，登录/云同步会挂。
判定的干净办法 —— **在页面上真的提交一次假账号登录，看错误码落在哪一层**：

| 现象 | 含义 |
|---|---|
| `AuthError / invalid_username_or_password`（`errorCode: 4043`） | ✅ 域名已授权，请求走到了**凭据校验** |
| `WEB_DOMAIN_NOT_AUTH` 类错误 / 预检失败 | ❌ 域名未加入白名单 |

实测网络层（`agent-browser network requests`）：
```
OPTIONS https://calcdaily-d5g2titwue91551fb.api.tcloudbasegateway.com/auth/v1/signin?client_id=…  204
POST    https://calcdaily-d5g2titwue91551fb.api.tcloudbasegateway.com/auth/v1/signin?client_id=…  400
```
**预检 204 = 网关接受了 `Origin: https://calcdaily.cn`**；POST 400 是业务层凭据错误。
若域名不在白名单，预检就不会返回允许头，POST 会被浏览器按 CORS 直接拦掉，
根本拿不到 400。所以「拿到 400」这一件事同时证明了域名授权 + 登录链路可通。

⚠️ 白名单是 **env 级、挂在 `api.tcloudbasegateway.com` 网关**上的，
所以 auth / 云数据库 / 云存储三者一次过，不用分别测。

### 两个已确认的缺口（都不是阻断项）

1. **`http://calcdaily.cn/` 返回 200，不强制跳 HTTPS**

# AI 连接稳定性实测（用户报「AI 连接很不稳定 / 一直出备用题 / 判不了等价形式」）

**产出**：新增 `tools/net-stability.mjs`（可复用探针，5 模式 × direct/proxy）
＋ 仓库根 `NETWORK-STABILITY-REPORT.md`。**未改任何生产代码。**

## 核心结论：连接是好的，问题在闸门

| 层 | 数字 |
|---|---|
| health 直连 | **60/60 + 30/30**，p50 100ms，后端自报 19~21ms，链路净开销 ~80ms |
| health 真实浏览器（走系统代理） | **10/10**，p50 **59ms**，max 149ms |
| health curl 走代理 | **仅 6~18/30**，`SSL_ERROR_SYSCALL` + 5 次挂起 600~1040s |
| generate（直连） | 失败 **0/36** 是网络原因 |

→ **「AI 连接不稳定」这个判断不成立。** curl 走代理的惨状**不代表浏览器**：
浏览器复用连接隧道，curl 每次新开一条。**不能用 curl 走代理的数字代表用户体验**（这是本次最大的测量陷阱）。

## 真正的原因：闸门拒稿，且强依赖考点

完整 50 格矩阵（钉死考点）：**25/50 = 50%**，全模块拆解
**derivative 2/18 = 11%** / limit 7/14 = 50% / integral 16/18 = 89%。

**0% 考点名单**（引擎结构上验不了 → Tier C → 必然拒稿）：
- `derivative / 隐函数求导`、`参数方程求导`、`分段点处的可导性`、`复合函数求导`
- `limit / 定积分定义求数列极限`

**★ 决定性对照**：导数模块，钉死考点 **5/18 = 28%**，而 `topic: null`
（真实用户默认，`chooseWeakTopic()` 多数返回 null）**18/18 = 100%**。
→ **只看评测矩阵会把产品说得比实际差得多。** 任何「钉考点」测出的成功率不能当用户体感。

**连锁效应（重要）**：`chooseWeakTopic()` 拿用户做错的考点当下次考点
→ 在「隐函数求导」上做错的学生会被反复喂这一考点 → 100% 备用题。
这是自适应逻辑与闸门口径的耦合缺陷。

## 判题「其他形式」：覆盖率其实很好

16 个等价改写用例（每条都配「原答案」对照，防用例本身无效）：
**对照 14/14 通过，改写被认对 13/14 = 92.9%**，全部由确定性引擎判（`method: deterministic`）。

唯一缺口：**前置常数**。`fb-int-05` 的 `\arctan x+C` 改写成 `C+\arctan x` → `uncertain`。
根因：`math-quality.js:1073 stripPlusC()` 只剥**尾部** `+C`（`/\+\s*\\?[Cc]\s*$/`），前置的管不到。

**这条和网络无关**：本地引擎先跑（`app.js:4352`），它返回 uncertain 才打网络（`app.js:4370`）。
所以网络好坏只影响「能不能问到模型」，不影响「模型能不能说对」（模型被设计成永不说对）。
→ 要改善只能**扩大引擎覆盖面**，不能放松模型权限。

## 放大器：闸门拒稿返回 HTTP 500

实测 25 次拒稿**全部 `http: 500`**。`cloudbase/deepseek/index.js:1290` 给拒稿错误设了
`error.code` 但**没设 `statusCode`** → 冒到顶层变 500。而
`app.js:2034 apiRetryable()` 对 `status >= 500` 返 true，`API_RETRY.generate.attempts = 2`
（唯一豁免是超时）。→ 推断一次拒稿最多烧 **4 次模型调用**、用户等 **~12s**。
（此条是**代码推断**，探针单次请求不重试；要坐实可看浏览器 `CalcDailyDiag` 的 retry 事件。）

## 测量过程中的坑（写进 MEMORY）

1. 🔴 **`curl --max-time` 在代理异常时兜不住**：实测 5 次挂起 600~1040 秒。
   必须同时给 `--connect-timeout`，并给整轮设总时长上限。
2. 🔴 **挂起会把本机 DNS 拖挂**：此后所有请求变 `Could not resolve host`，
   污染了后续 3 轮测量（约 78 分钟）。集中出现该错误时**先停下重跑，不要采信**。
3. **对照组不是可选项**：等价形式用例若对照失败，整条不可采信。
4. **`--loose-topic` 是必需的口径开关**，不是可选优化。
