## AI 出题链路诊断（只读排查，未改代码）

排查用户反馈的两个症状：连接不稳定经常断开、出题错误多。

### 硬证据

线上后端仍存活：`GET /api/deepseek?health=1` → 200，0.68s。

真实调用 30 次 `action=generate`（单题）实测通过率：

| 模块 | L4 | L8 | L10 | L12 |
|---|---|---|---|---|
| limit | 3/3 | 3/3 | — | 3/3 |
| derivative | 3/3 | 1/3 | 0/3 | 0/3 |
| integral | 3/3 | 0/3 | — | 0/3 |

L4 全过；L8 以上导数/积分大面积失败，返回 `{"error":"Question quality gate rejected draft"}` HTTP 500。
失败耗时约为成功（~3.4s）的 2 倍，说明两次尝试都跑完了。

本地用 math-quality.js 复现：
- `Quality.compare` 对符号答案（`\frac{x^2}{2}+C`、`\ln 2`、`e^x(...)+C`）一律返回 `uncertain`；
  而 `reviewQuestion` 只在 `independent === 'not_equivalent'` 时拒绝 → 符号答案的独立核对等于放行。
- `-\frac{1}{2}` vs `1/2` 也是 `uncertain`，符号错误漏检。
- `issues()` 只认「答案为 X / 结果是 X」这一种很窄的写法，`结果 = 1`、`\frac{}{}` 都漏。

### 定位到的两个核心缺陷

1. **客户端重建题目对象导致审核快照失效**（app.js ~4005-4105 vs math-quality.js `content()`）
   服务端 `content(q)` 用的是模型原始 `q.topic`（缺省时 JSON.stringify 成 `null`）；
   客户端重建时把 topic 兜成 `plan.topic || '综合基础'` → 两个快照不相等
   → `trustedQuestion()` / `MathQuality.approved()` 判为不可信 → 渲染出
   「这道题存在异常，已自动作废」。审核本身是好的，是客户端自己改坏了。
   tests/reliability.cjs 的 `draft()` 永远带 topic，所以 28/28 通过也测不到这条。

2. **质量闸门在高难度下必然拒绝**
   通过条件 = 6 个布尔严格 `===true` + confidence≥0.9 + issues 为空 + 独立答案不矛盾。
   难度越高，reviewer 越不可能给 ≥0.9 的置信度、越容易把 `difficulty_reasonable` 判 false
   → 高难度题系统性被拒 → 前端退回 12 题备用库（每模块仅 4 道，取难度最近的一道，不看是否做过）。

### 连接侧的缺陷

- `apiCall` 无任何重试；一次失败 → `generateOneQuestion` 直接吞掉转备用题。
- `checkApiHealth()` 的 fetch 完全没有超时（只有 `apiCall` 用了 AbortController）。
- 超时 abort 的报错（`The user aborted a request.` / `signal is aborted without reason`）
  匹配不上 `shortApiError` 里的 `/timeout|超时/` → 用户看到半截英文原文。
- 服务端 `generateQuestions` 两次尝试之间无退避，失败立刻重发；最坏 2×(45+45)=180s
  对客户端 190s 上限几乎顶死。
- `callDeepSeek` 里 `response.json()` 无 try/catch，网关返回 HTML 时报
  `Unexpected token '<'`，且丢掉 statusCode → 变成含义不明的 500。
- storage.js 的 `syncNow` 无超时、无重试、无 `online` 事件监听，全部串在 `syncTail`
  一条链上；一个卡住的请求会永久堵死后续所有同步。
- 项目里没有任何 `addEventListener('online'|'offline')`、也没有 `navigator.onLine` 判断。

- bash 的 `grep` 在 app.js/storage.js 上行为异常（多分支模式匹配不到），改用 Grep 工具。

## 第二轮（实施 CalcDaily v1.1）— 进度与真问题

### 已完成

**1. math-quality.js 重写为 quality-v2**（已同步到 cloudbase/deepseek/ 副本）
- 新增确定性验证：`verifyLimit` / `verifyDerivative` / `verifyIntegral` / `verifyAnswerAgainstQuestion`
- 数值采样避开抵消陷阱：步长固定 1e-2~1e-4 + Richardson 外推；极限用「粗/细两套步长交叉核对」，
  不一致就不下结论（实测 e^x-1-x-x^2/2 在 1e-6 会算出 -37.8）
- Hard/Soft gate 拆分：4 个硬字段 + confidence 闸门；topic/difficulty 只作元数据，永不拒绝
- `judgeOutcome()`：错误状态分类（本轮的架构决策，见下）
- `issues()` 改用 `verifyAnswerAgainstQuestion`（结构式校验）。原来自比较恒等，等于没查

**2. 修掉两个真实解析缺陷**（都是「正确答案被判不确定」的来源）
- `expandFrac` 原来用 `[^{}]*` 抓分子分母，遇到嵌套花括号就整条崩掉。
  受影响的是**几乎所有高数答案**：`\frac{x}{\sqrt{1+x^2}}`、`\frac{e^{2x}}{2}`、
  `\frac{(1+x^2)^{\frac{3}{2}}}{3}` → infix 变成 `fracxsqrt 1+x^2` 这种垃圾。
  改为花括号平衡匹配 + 递归。
- `\cos^2 x` 这类**函数幂记号**解析不了（infix 是 `cos ^2 x`）。新增 `expandFuncPowers`。
  只认整数幂 ≥2：`\cos^{-1}` 在「反函数 vs 倒数」之间含糊，保持 uncertain 更安全。
- 附带：`\sqrt` 原来被命令大扫描吃掉，导致 `sqrt{1+x^2}` 丢掉括号变成 `sqrt 1+x^2`，
  求值成 `sqrt(1)+x^2` —— **静默算错**。现在 `expandSqrt` 用平衡括号，并在前面补显式 `*`。

**3. 精度缺陷两处**（老测试抓住了，确实是引擎的问题）
- `isExactForm` 原来把 `e` 写法一律踢出精确比较 → `0` vs `1e-15` 判等价、`0` vs `1e-400` 判等价。
  现在只排除带小数点的字面量（那才是人的四舍五入，`1/6` vs `0.1666666667` 仍需容差比较）。
- `hardGate` 用 `Number()` 强转 confidence，`'0.99'` 字符串被当高置信度放过；
  而服务端 `reviewQuestion` 自己要求 `typeof === 'number'`。已收紧为同一条规则。

**4. fallback-bank.js（60 道，fallback-v2）+ 接入前端**
- 旧的内联题库只有 12 道（每模块 4 道）且含一道错答案（`ln(1+sin x)` 极限写成 `-1/6`，正确 `+1/6`）
- 新题库每模块 20 道，**60/60 都能被引擎确定性判定**（初次只能判 52，靠上面两个解析修复补到 60）
- `pick()` 用 难度接近 + 考点相关 + 排除最近做过；`fallbackQuestion` 改用 `FallbackBank.pick`
- `recentFallbackIds()` 从 `state.history` 按题面反查 id（历史项不带 source/bankId，所以不能按 id 查）
- index.html 在 app.js **之前**加载 fallback-bank.js

### 本轮最重要的发现：网络故障被报成「题目有问题」

真机复现（拦截出题/判题接口）：提交一个引擎判不了的答案 → 判题 API 挂 → 界面显示
**「这道题存在异常，已自动作废」**，题目丢掉、用户答案丢掉、练习卡住。
但题是验证过的题库题，问题在网络。

`judgeAnswer` 原来把三种完全不同的失败压成一个 `{trusted:false}`：
题目不可信 / 判题服务连不上 / 判题返回不可用。上层只能一刀切。
现已拆开（`MathQuality.JUDGE_REASONS` + `judgeOutcome()` 决定处置）：
- `question_untrusted` → 作废该题
- `judge_unavailable` / `judge_uncertain` → **保留题目和答案**，按钮变「重试提交」
- 未知形态一律走重试（宁可让用户再点一次，也不误作废题目）

**教训**：`trusted:false` 这种二值设计会吞掉原因。凡是「失败」需要不同处置的地方，
必须把原因一起传出来。

## Task #3 完成：服务端 Hard/Soft 闸门拆分 + Judge 收窄（本轮）

### 服务端（两份副本，业务逻辑段逐字节一致）

`const PIPELINE = {` 是业务逻辑的哨兵行，其后到文件末尾必须逐字节相同：

```
api/deepseek.js                ← Vercel handler
cloudbase/deepseek/index.js    ← 云托管常驻服务（线上实际生效的那份）
```

- `PIPELINE` / `versions()`：每个响应与每条日志都带 `protocol/generator/reviewer/judge/math_engine`
  （50/200 题评测要能按版本归因，中途改过流水线才不至于混批）
- `CALL_POLICY` 按标签给重试预算：generate 1 次 / 40s（外层已有 2 次尝试，
  内层再重试会把客户端 190s 预算顶死）；review 2/35s、judge 2/20s、evaluate 2/20s
- `isRetryable`：429 / 5xx / TimeoutError / AbortError / TypeError(断网) 才重试；
  4xx（鉴权、参数）与非 JSON 响应一律直接抛
- `backoffDelay(attempt, base)`：指数 + 30% 抖动，上限 4000ms
- `readUpstreamJson`：网关 502 回 HTML 时抛 `UPSTREAM_PROTOCOL_ERROR` 并保留真实状态码，
  不再把 502 伪装成「Unexpected token '<'」
- `reviewQuestion`：确定性引擎先跑（它能判的不消耗模型调用）→ 模型复审 →
  `evaluateHardReview` 只采信 4 个硬布尔 + 独立答案一致性 + `canonical_suspected`；
  **自由文本 issues 只进 `reviewer_notes`，不参与拒稿**
- `buildMetadataCorrection` + `applyMetadataCorrection`：soft 字段不符 → 写
  `displayTopic` / `displayDifficulty` / `metadataCorrection`，**canonical 一个字不动**
- `judgeAnswer` 收窄：不发 solution、反馈按 verdict 给固定文案、
  新增 `canonical_suspected`（怀疑标准答案 → 作废但不判学生错）、
  上游故障返回 `reason: 'judge_unavailable'`

### 前端

- `trustedQuestion` 放宽：历史复习条目可能没有 `source`/`bankId`/`verification`，
  只要题面与验证过的题库逐字段一致就认可
- `questionDifficultyLabel` 优先级：**displayDifficulty 最前**。
  因为 `calibratedDifficulty = calibrateDifficulty(provisionalDifficulty)` 是生成时算的，
  标定点不足时原样返回 provisional —— 只是同一个 AI 猜测的单调变换，不比 provisional 更权威
- **修掉一个真 bug**：`judgeAnswer` 原来只认 `reason === 'question_untrusted'`，
  其余一律归到 `judge_uncertain` —— 服务端明确说的 `judge_unavailable` 被降级，
  界面于是把「连不上判题服务」说成「判题服务没给出结论」

### 复习队列：canonical 字段与 verification 快照必须整体替换

`queueWrongQuestion` 按 `topicKey = module:topic` 建槽位，同考点第二道错题会复用条目。
旧写法逐个覆盖 instruction/expression/prompt/answer/solution，**快照留在创建时那道题上**，
条目从此持有一份描述另一道题的验证快照（旧写法还给空 topic 补 `'综合基础'`，等于伪造考点）。

治法：新增 `CANONICAL_FIELDS` + `bindReviewQuestion(item, question)` ——
只提供整体替换，不提供逐字段写入的入口。

**汇报纪律（差点说错）**：复习会话**不是**把条目当题目渲染，而是拿它的题面当
`referenceQuestion` 重新生成一道题。所以这条是「持久化数据自相矛盾」的隐患，
不是当前可见的「题目存在异常」。一开始的因果链说错了，核实后改掉了措辞和注释。
