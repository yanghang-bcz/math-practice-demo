## 「AI 服务未连接」排查（用户报障，已定位）

**结论：不是线上故障，是本机系统代理太慢，撞上健康检查的 8 秒超时。**
证据链（全部可复现）：

1. 线上一切正常：`?health=1` 200；真实浏览器打开生产域名 → 状态栏是
   「DeepSeek 已连接 · 协议 v2」，页面内跨域 fetch 探针 200 / 661ms。
2. 线上前端仍是 `ab0e0a0` 版（7/7 逐字节一致），**没有 CI/CD**（无 `.github/workflows`）
   → 上一轮的 push 不可能触发部署。
3. **macOS 系统代理是开着的**：`scutil --proxy` → HTTP/HTTPS/SOCKS 全指向
   `127.0.0.1:7897`（Clash 类客户端）。浏览器默认走它，而我的 curl/Playwright 都不走。
4. 经该代理访问后端 health：**2.1s ~ 10.8s**（连续 8 次里有 2 次 = 9.3s / 10.8s），
   而响应头 `x-cloudbase-upstream-timecost` 显示**后端自己只花 27~200ms** —— 慢在代理这一跳。
   直连只要 **0.15s**（站点首页直连 0.36s，经代理 3.2s）。
5. `app.js:2302` `HEALTH_TIMEOUT_MS = 8000` → 超 8s 就 `AbortController.abort()`
   → `catch` 里 `apiHealthy = false` → `renderApiStatus()` 显示「AI 服务未连接」。
6. **端到端复现**（`agent-browser` + `open --init-script` 给 health 请求注入 9s 延迟）：
   界面确实变成「AI 服务未连接」，应用自己的诊断环记
   `{action:'health', kind:'generate_timeout', outcome:'unreachable', message:'signal is aborted without reason'}`。
   截图存 `.workbuddy/evidence/ai-not-connected-badge.png`。

**影响面比看起来小**：`apiHealthy` **只被 `renderApiStatus()` 读取**（2633/2647/2665），
不 gate 任何请求；出题超时是 **60s**、判题 **22s**（`API_TIMEOUTS`，app.js:1924），
所以经代理仍能正常出题，只是慢。**是状态栏这句话在误导人**，不是功能坏了。

**给用户的一句话解法**：把 `tcloudbase.com` 加进代理直连规则，或关掉系统代理。

**产品侧可改（待定，未动手）**：8s 对「代理绕境外 + 云函数冷启动」太紧；
且超时后再无自动重试（`checkApiHealth` 只在 init 与 `markApiRequestFailure` 里调）。
建议：超时自动重试一次，或把「超时」与「未连接」分成两种文案。

### 复现用的手法（值得留档）
`agent-browser open <url> --init-script <js>` + 在 init script 里包一层 `window.fetch`
给指定 URL 人为加延迟 —— 这是复现「前端超时类」故障的干净办法，不用改任何产品代码。
